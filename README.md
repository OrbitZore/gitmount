# gitfs — mount a git repository as a read-only filesystem

`mount.gitfs` mounts a local git repository (bare or non-bare) as a
**read-only** FUSE filesystem. Every branch, tag, remote-tracking ref and
commit is presented as a directory containing the full snapshot of its
tree, so any revision can be browsed with ordinary tools (`ls`, `cat`,
`grep`, diff tools) without `git checkout`, `git worktree` or
`git archive`.

```
/mnt/gitfs/
├── branch/      # local branches (nested names render as directories)
├── tag/         # tags (annotated and lightweight; peeled to commits)
├── commit/      # any commit, by full oid only (never enumerable)
├── remote/      # remote-tracking branches <remote>/<branch>
├── HEAD/        # snapshot of the current HEAD
├── commits      # read-only list of every reachable commit oid
└── .gitfs.json  # mount metadata
```

Design document: [rfc/0000-gitfs.md](rfc/0000-gitfs.md) (Chinese, normative).
User-facing semantics: [docs/filesystem-semantics.md](docs/filesystem-semantics.md).
Manual page: [docs/mount.gitfs.8](docs/mount.gitfs.8).

- C++17, [libgit2](https://libgit2.com) ≥ 1.4, [libfuse3](https://github.com/libfuse/libfuse) ≥ 3.10, CMake ≥ 3.16
- Linux only (v0.1); no network access, no `git` subprocesses
- Read-only by construction: every write path returns `EROFS`; mounts are
  forced `ro,nosuid,nodev,default_permissions`
- GPL-3.0-or-later

## Quick start

Build dependencies: a C++17 compiler, CMake ≥ 3.16, pkg-config,
`libgit2-dev` (≥ 1.4), `libfuse3-dev` (≥ 3.10). Unit tests fetch
[Catch2 v3](https://github.com/catchorg/Catch2) via CMake FetchContent
(network required at configure time, or preinstall Catch2 and set
`FETCHCONTENT_SOURCE_DIR_CATCH2`).

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build
ctest --test-dir build              # unit + integration (skips w/o /dev/fuse)
sudo cmake --install build          # $(sbindir)/mount.gitfs + man8 page
```

Mounting — the three equivalent forms:

```sh
mount -t gitfs /path/to/repo.git /mnt/gitfs     # via mount(8)
mount /mnt/gitfs                                # via /etc/fstab entry
mount.gitfs /path/to/repo.git /mnt/gitfs        # direct
```

`/etc/fstab` example:

```
/srv/repos/linux.git  /mnt/linux  gitfs  ro,noatime,nofail  0  0
```

Unmount with `umount <mountpoint>` (or `fusermount3 -u`). The daemon also
exits gracefully on `SIGINT`/`SIGTERM`.

### Options

```
-o blob-cache-size=<MiB>    blob LRU cache limit (default 64)
-o tree-cache-size=<MiB>    libgit2 tree/commit cache budget (default 256)
--blob-cache-size <MiB>     same as -o blob-cache-size=<MiB>
--tree-cache-size <MiB>     same as -o tree-cache-size=<MiB>
--foreground                stay in the foreground (no daemonizing)
-f                          fake: validate arguments and repository, no mount
-v, --verbose               resolution logs + one line per blob decompression
```

`rw` in `-o` is accepted as a no-op with a warning (`mount(8)` pre-seeds it
unconditionally). Irrelevant VFS keys (`noatime`, `nofail`, `user`, ...) are
accepted and ignored. `suid`, `dev`, `remount`, `uid=`, `gid=`, `umask=`,
`context=`-family options and `subtype=` are rejected — the read-only
baseline is not negotiable. Unknown keys go to libfuse (e.g.
`kernel_cache`, `allow_other`).

Exit codes: `0` success, `1` parameter error, `2` repository unreadable,
`3` mount failure.

## Semantics you should know before relying on gitfs

These are the sharp edges pinned by the design document; the full stable
contract is in [docs/filesystem-semantics.md](docs/filesystem-semantics.md).

- **`/commits` pauses on first open.** The list is generated by a full
  `rev-list`-equivalent walk on the first `open()` — on huge repositories
  (the Linux kernel: ~1.1M commits, ~45 MB of text) the first `cat
  /mnt/gitfs/commits` blocks for seconds. `stat` before the first open
  reports size 0 and never triggers the walk.
- **Oversized blobs pin at open.** A blob at or above the blob-cache limit
  is fully decompressed once at `open()` and held in memory until the file
  is closed. Opening a multi-gigabyte blob therefore takes seconds and its
  memory is bounded by the number of concurrent open file descriptors.
  Concurrent requests are not blocked meanwhile (decompression happens
  outside the global lock).
- **Concurrent cache misses may decompress twice, briefly.** The blob LRU
  loads outside the lock; two racing readers of the same cold blob may each
  decompress it once (the loser's copy is dropped immediately).
- **Disable gc while mounted (recommended).** gitfs never locks the
  repository; if an external `git gc`/`git prune` deletes or rewrites
  objects that a request still needs, that request fails transiently with
  `ENOENT`/`EIO` and recovers once gc finishes. Either accept the transient
  errors or run `git config gc.auto 0` on long-mounted repositories.
- **st_ino memory bounds.** Inode numbers are derived from path hashes and
  registered lazily; the registry never recycles within a mount. It costs
  roughly (path bytes + tens of bytes) per distinct path actually touched —
  order tens of MB for a million distinct paths.
- **Ref updates are live.** New branches/tags appear without remounting;
  already-resolved old objects remain accessible while they exist in the
  object database. `refs/replace` is never honored (gitfs shows original
  objects, like `git --no-replace-objects`).
- **`/commit` cannot be listed.** `ls /mnt/gitfs/commit` is always empty —
  use `grep ^<prefix> /mnt/gitfs/commits` to resolve an oid prefix.

## FAQ

**Can I write through the mount?** No — every write path returns `EROFS`.
gitfs is a read-only data plane by design.

**Is it safe to mount untrusted repositories?** Symlink targets are
repository-controlled and passed through verbatim (like `git checkout`),
and paths are confined to the mountpoint by the VFS. Do not browse
untrusted repositories as root.

**sha256 repositories?** Yes — oids are 64 hex chars throughout
(`/commit/<64-hex>`, the `commits` list, `.gitfs.json`).

**Why is `df` showing 100% usage?** `statfs` reports the local object
database size as the volume size and zero free space: a read-only volume
has no writable space, and saying so explicitly beats reporting 0% used.
Alternates-backed storage is not counted (a verbose note is logged when
alternates are detected).

**`ls` shows strange characters for some files?** Tree entry names are
passed through as raw bytes; a non-UTF-8 filename shows up exactly as it
would after `git checkout` — no escaping, no renaming.

**How do I match mounts?** `/proc/mounts` shows the type as
`fuse.gitfs` (FUSE subtype) with source `gitfs`; `findmnt -t fuse.gitfs`
lists gitfs mounts.
